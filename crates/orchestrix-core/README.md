# Orchestrix Core — runtime, domain, persistence and local Git

OX-003 provides the Rust consumer of portable runtime contract 1.1: validation, admission checks and observation of one owned attempt. The runtime contract, domain and policy remain independent of OS process handles, provider messages and database types. Infrastructure modules implement local effects separately, without Node, Tauri or an autonomous planner. The [local daemon/recovery contract](../../docs/contracts/local-daemon.md) extends the manual worker without introducing another execution engine.

OX-004 adds the [pure domain](src/domain/mod.rs): typed identities, projects/repositories, connections/shared capacity, conversations/session references, versioned modes/profiles, attempts, tasks and Runs. It consumes the same runtime observer and keeps execution outcome, output production, artifact acceptance, internal integration and final application separate. [Domain contract/API rules](../../docs/contracts/domain-and-states.md) and [original acceptance evidence](../../docs/research/ox-004-domain-increment.md) describe guarded operations. The domain module remains independent of SQL and actual process/Git/check services.

OX-005 adds [SQLite persistence](src/persistence/mod.rs), outside the domain, using rusqlite 0.40.2 with bundled SQLite 3.53.2. It stores current state, evidence, append-only audit events and idempotent command results transactionally. Validated checkpoints preserve private invariants, observer budgets/quarantine, exact artifact/approval versions and historical definitions. [Persistence contract](../../docs/contracts/persistence.md) and [ADR-0006](../../docs/adr/0006-synchronous-sqlite-persistence.md) define the boundary; [current status](../../docs/DEVELOPMENT_STATUS.md) owns the ticket/milestone completion decision.

OX-006 adds the separate [local Git infrastructure](src/git/mod.rs), with an installed Git CLI and schema migration 3. [Worktree and capture contract](../../docs/contracts/git-worktrees.md) defines pinned bases, directory authority, durable ownership, bounded exact evidence and conservative cleanup. This infrastructure uses OS processes; it does not move them into the pure domain or implement the runtime supervisor.

OX-003 is accepted for the first local single-account runtime under [portable input profile revision 1](../../docs/contracts/runtime-input-profile.md). This explicitly replaces the previous permissive experimental decoder; normalized v1.0/v1.1 data remains compatible, while ambiguous/nonportable inputs are rejected without timezone inference. Semantic wire version and codec revision are separate. [Acceptance and verification](../../docs/research/portable-runtime-input-increment.md) do not close M0 or production/provider gates.

`runtime_contract` exposes validated `RuntimeDescriptor`/`RuntimeRequest` wrappers, `RuntimeObserver`, `EventOrigin`, `Limits`, normalization, capability decisions and explicit admission validation. JSON internals are private and immutable through the public wrapper API; snapshots are owned copies. The host passes provenance separately, and must actually establish supervisor ownership. Validating a frame/configuration fact does not authorize dispatch or certify OS containment.

The consumer preserves requested/effective settings, model-specific levels/unknowns, local connection/revision/session/attempt/turn references, sequence/version/budgets, legacy strict and factual 1.1 transitions, typed errors/quarantine, interruption and independent process/helper/stream/tree evidence. It never derives a remote terminal from process termination. No hidden reasoning or runtime conversation memory is required.

The application-layer [`connections`](src/connections.rs) service adds daemon-owned runtime-managed linking, lifecycle revisions, metadata diagnostics and future-admission guards. It reuses the existing runtime metadata service and Core store (migration 8), preserving local edit versus binding revisions, exact command receipts and historical observations. The [daemon connection extension](../../docs/contracts/local-daemon.md#runtime-managed-connections-extension) defines its host-only/private boundary; it does not implement an OAuth engine, credential vault or independent quota.

## Run

Requires Rust/Cargo and the platform's linker/toolchain. The development Windows environment uses Rust **1.99.0**, x64/MSVC; no MSRV or macOS/Linux execution is certified by that result. Cargo.lock fixes dependency versions; it does not install providers or run inference.

```powershell
cargo check --workspace --all-targets --locked
cargo test --workspace --locked
cargo build --workspace --locked
cargo build --workspace --examples --locked
cd tools/runtime-harness
npm.cmd run check:conformance
npm.cmd run test:rust-core
```

After dependency download, these Cargo commands also work with `--offline`. The minimal rustup install used for this increment does not require an IDE or new system components; existing MSVC/SDK were reused.

The CLI and `orchestrix-supervisor` helper must be built/deployed together. Integration tests build the binaries through Cargo; a consumer embedding the worker must package the trusted sibling helper explicitly. Missing support blocks launch rather than reducing containment guarantees.

## Durable commands and restoration

`Store::open(absolute_path)` opens an explicit local file whose parent directory already exists and runs versioned migrations; it refuses future/incompatible schemas without recreation. `load()` returns a detached read-only `SavedState`, not a resumed runtime or selected UI conversation. Short writes use WAL/FULL, foreign keys, a 250 ms busy timeout and an immediate writer transaction.

`Request` carries a `LocalRef` scope/key, `expected_revision` and typed `Command`. `Store::execute()` returns a `Receipt` with a persisted `CommandResult`, disposition and replay flag. A committed key binds the command content **and original expected revision**; identical replay returns the original result without additional effects. Stale revisions on unused keys abort without reserving them. The store stages changes separately and commits before reporting them; business failure evidence and technical rollback have distinct outcomes.

`Command::run(id, action)` and `Command::create_run(run)` are constructors for the owning domain operations. `RunAction::assign(task, attempt, snapshot)` reserves a local attempt with an `AttemptSnapshot` referencing existing immutable mode/profile/context/configuration definitions and diagnostic observations. Reservation does not dispatch or prove external exactly-once execution. Conversation Send/Reply/Attach/SaveDraft/LinkWork commands preserve saved history and first-nonempty-send semantics. `SaveCapacityGroup` stores the existing domain's membership and Unknown/Observed evidence without inferring independent quotas or adding a quota service.

The separate [document records](src/persistence_records.rs) module validates versioned definitions and scoped diagnostic histories; [privacy](src/persistence_privacy.rs) applies bounded sanitization before storage. A failed diagnostic refresh preserves the last successful observation and its original dates. Domain `checkpoint()` / `restore_checkpoint()` and observer equivalents are validated formats, not general-purpose entity deserialization.

[Workflow tests](tests/persistence_workflow.rs) exercise file-backed Run → Task → attempt → artifact/evidence → event → reopen → continued delivery, preserved negative integration/application evidence, stale references, global session bindings, quarantine and all three injected write boundaries. Nine parent tests pass, including OX-006 record atomicity; the separate-process parent explicitly invokes its ignored helper to reload an Approved Task and continue integration. The additional storage tests in [persistence/tests.rs](src/persistence/tests.rs) cover migrations, contention, command replay and commit-before-reply loss. Ignored child helpers are executed by their parent tests rather than counted as untested capability.

```powershell
cargo test --package orchestrix-core --test persistence_workflow --locked --offline
cargo test --package orchestrix-core --test persistence_boundary --locked --offline
cargo test --package orchestrix-core --test persistence_records --locked --offline
```

These tests use isolated temporary files and synthetic observations. Rollback injection is not a power-loss recovery test; no provider login, live inference, Git project operation or process reconciliation is performed.

## Registered attempt to durable Git artifact

`WorktreeService::create(&mut Store, &CreateWorktree)` requires an existing Project/Repository/Run/Task/Attempt, its granted directory reference, an existing absolute authorized root, and a full pinned commit OID matching the attempt's base. It commits intent, creates owned refs and a locked worktree, materializes raw blobs without checkout/filter execution, then confirms creation in a separate transaction. A retry verifies retained ownership rather than adopting a matching name.

`capture()` records immutable base/index/working content and an exact patch with SHA-256 provenance. A committed capture key replays its original evidence after edits, reopen or removal. It does not publish an accepted domain artifact, run project checks or approve/apply changes. `remove()` accepts only an inactive registered attempt at its exact clean pinned base, with no untracked, ignored or excluded content; ownership/base/completion anchors and persisted evidence remain. Dirty or uniquely committed work is preserved.

The initial profile supports bounded regular UTF-8 files with mode `100644`; unsupported bases, links, submodules, modified binaries, configured filters and unsafe exact content are refused. Limits and crash gaps are explicit in the contract. These checks do not provide OS containment or protection against a hostile writer replacing metadata between operations. Loading SQLite never executes Git.

[Real Git + SQLite workflow tests](tests/git_worktrees.rs) cover isolation, main-checkout preservation, replay, another process, ownership collisions and recovery after Git effects but before SQL confirmation. [Capture tests](tests/git_capture.rs) cover staged/working differences, additions/deletions, concurrency, exclusions and patch syntax. Temporary fixtures use installed Git without providers, project scripts or network access. [Increment evidence](../../docs/research/ox-006-git-increment.md) records results and remaining boundaries.

## Conformance and adapter integration

[runtime-conformance-v1.json](tests/fixtures/runtime-conformance-v1.json) is a versioned, deterministic JSON corpus: **245 cases/935 operations** with construction results and each operation/event/snapshot/error checkpoint from the JavaScript executable specification. It includes seven fake scenarios, normalized existing Codex evidence and the three explicitly synthetic replay cases, plus adversarial identity, provenance, protocol, compatibility, limits, policy and output checks. The preceding 104 cases remain identical; new raw/timestamp/error-priority cases identify the codec profile explicitly. [Independent expected vectors](../../tools/runtime-harness/fixtures/portable-input-v1.json) prevent relying solely on the oracle. The future refresh policy is not implemented by this corpus.

[export-conformance.mjs](../../tools/runtime-harness/export-conformance.mjs) rebuilds the corpus offline from the existing contract/fake/replay and input hashes. `--check` checks committed bytes without overwriting; `export:conformance` is an explicit regeneration. Review semantic changes to expectations instead of using regeneration to bless a regression. Rust tests load the committed JSON directly and need no Node. They compare complete normalized data and snapshots, including events and byte budgets; JSON object ordering is immaterial.

The corpus and Cargo/Rust sources use LF through repository attributes. Input hashes explicitly use `lf-normalized-input-bytes`; CRLF/LF variants produce identical golden data without rewriting historical reports. This prevents a Windows checkout from making the generated corpus stale while keeping raw historical hashes separate.

[runtime_observe](examples/runtime_observe.rs) is an offline example reading a bounded **4 MiB trusted host bundle** from stdin: `{inputProfile: {id: "orchestrix-runtime-json", revision: 1}, descriptor, request, frames: [{origin, frame}]}`. Missing/unsupported profiles return `version`; semantic wire minors cannot downgrade decoding. It sends frames to the same library consumer, returns normalized output or a fixed typed error, and performs no provider/process/storage effects. It is a test/diagnostic bridge, not the future local daemon or an endpoint granting provider-supplied supervisor assertions.

The separate [adapter → Rust tests](../../tools/runtime-harness/tests/rust-core.spec.mjs) require that example to be built; they launch only the own Node fake app-server and this Rust consumer. They are opt-in from the Node harness because its default suite does not require a Rust toolchain. `success`, cooperative interruption, rate limit and malformed transport reports are normalized by the actual adapter, then checked against the Rust result. The provider-neutral fake uses the same executable. A successful historical replay is translation evidence, not new authentication or live containment.

## Remaining boundaries

The portable parser does not establish credential identity/entitlement, active execution or filesystem checks. The separate Rust [runtime adapter](src/runtime/mod.rs), [policy](src/policy/mod.rs), [worker](src/worker.rs), [evaluators](src/evaluator.rs) and [Windows process crate](../orchestrix-process/src/lib.rs) implement the integrated manual path. Their current acceptance and live boundaries are recorded in [status](../../docs/DEVELOPMENT_STATUS.md); the experimental Node harness remains a reference/proof tool, not a production dependency.

The [Desktop application service](src/desktop.rs) adds typed project/conversation/settings operations and bounded SQLite projections for the [native Tauri client](../../apps/desktop/README.md). The renderer never receives SQLite access, runtime credentials or unrestricted filesystem/process operations. The separate [review service](src/review.rs) retains structured independent verdicts and bounded corrections on the original Task/Run; its schema-6 records, adapter checks and provider-proof limits are specified in the [worker contract](../../docs/contracts/manual-worker.md#independent-review-and-bounded-correction). Neither a verified worker nor an accepted review alone applies code to the user's destination.

The OX-014 [integration service](src/integration.rs) adds a separate guarded application path and [schema-7 records](src/persistence/integration.rs). The initial profile prepares one exact verified/reviewed code task in a Run-owned Git worktree, runs authorized combined checks, versions a candidate, then requires exact-base approval and explicit destination application. Short intention/confirmation transactions surround supervised Git/check effects. Recovery distinguishes a confirmed own ref update from an uncertain partial file update; it never repeats uncertain application automatically. [Contract/profile limits](../../docs/contracts/git-worktrees.md#serial-integration-and-explicit-application), [real disposable-Git tests](tests/serial_integration.rs) and current status distinguish implementation from executed acceptance. Historical integration inspection uses a bounded projection; physical revalidation is a separate journaled background operation.

The ignored Windows unit `git::integration::diagnostics::scoped_inspect_from_readonly_export` measures one read-only inspection in a new owned Job, without opening a Store, reconciling or replaying an integration. Set `ORCHESTRIX_DIAGNOSTIC_INTENT` to an explicitly authorized fixture's exported `IntegrationIntent` and `ORCHESTRIX_DIAGNOSTIC_INTENT_SHA256` to its exact SHA-256, then use `cargo test -p orchestrix-core --lib git::integration::diagnostics::scoped_inspect_from_readonly_export --locked --offline -- --ignored --exact --test-threads=1`. It requires the built supervisor, confines target/common-Git/worktree paths beneath the export's fixture directory, compares their complete bounded inventories before/after, and records static codes/counts/timings/hashes in its report under `artifacts/diagnostics`, without raw errors, commands or ownership authority. Its 120 s diagnostic ceiling terminates only the new diagnostic Job; production's 300 s Job and 15 s/8 MiB Git command limits remain unchanged. A successful isolated inspection does not prove an entire integration fits its budget.

The [manual-worker contract](../../docs/contracts/manual-worker.md) defines schema 1, cache validity, native effort translation, exact check binding, short SQLite operations, schema 4 and the initial Windows/serial profile. [Manual task manifest](../../docs/examples/manual-task.example.json), `cargo run --bin orchestrix -- help` and [integrated tests](tests/manual_worker.rs) provide the minimal entry. `run` explicitly opts into live Codex or a labelled synthetic runtime; `status` never starts a runtime. Source/worktree directories and SQLite authority are separate. A per-database OS host lease prevents concurrent hosts and lets status inspect active work without declaring a false crash. An interrupted host releases the lease, but an uncertain attempt is never retried automatically.

OX-010/011 add [daemon/API/CLI](src/daemon.rs), schema 5 [command journal and event feed](src/persistence/daemon.rs), [reconciliation/continuity](src/recovery.rs) and a [trusted Rust keeper](src/recovery_guardian.rs). The Windows named-pipe transport restricts access to the current user and bounds frames/I/O. A daemon owns operational access and one serial worker; clients share the API intended for the future Desktop. Startup reconciles before binding and starts suspended. Suspend, cancel, snapshots, events, continuity and intervention require no model. Reads explicitly distinguish historical evidence from current verification.

The keeper holds the exact Job before runtime launch; authorized checks share that scope. After host death/finish/deadline, it seals new process admission before terminating members and certifying zero active processes. Its private receipt proves local closure only. Exact-revision intervention may set eligible incidents aside while preserving native uncertainty, artifacts and command identity; it never redispatches the old task. Missing/corrupt evidence remains blocked. Git retains OX-006 limitations; a local receipt is neither a provider terminal nor power-loss proof. [Daemon tests](tests/local_daemon.rs) and [crash recovery tests](tests/worker_recovery.rs) use real Windows processes/Git/SQLite with synthetic runtime; [current status](../../docs/DEVELOPMENT_STATUS.md) records their acceptance separately from the earlier live Codex proof.

The [input profile](../../docs/contracts/runtime-input-profile.md) defines strict Gregorian/offset timestamps, finite binary64 JSON numbers and Unicode scalar strings. Normalized UTC milliseconds are idempotent; invalid/ambiguous legacy strings never become evidence. This is scoped conformance, not equivalence with every permissive `Date.parse` or arbitrary JavaScript input. Lexical validation includes ignored/overwritten fields; projection validates/skips compatible deep unknown data, including the existing 500-level regressions. Typed invalid-field priorities and numeric rounding match the compared inputs. The example's outer host-bundle decoder remains bounded and is not a production transport. Frame/collection bounds do not certify global memory usage, durability or cross-platform runtime support.

See [contract](../../docs/contracts/runtime-contract-v1.md), [portable input acceptance](../../docs/research/portable-runtime-input-increment.md), [preceding Rust evidence](../../docs/research/rust-runtime-contract-increment.md) and the [backlog](../../docs/DEVELOPMENT_BACKLOG.md). Independent artifact review, final integration/application and Desktop retain their own dependencies; local fixtures do not complete M0 or certify live provider controls. Preventive capacity reserves, contextual multiagent scheduling and actual orchestrator transfer remain planned under [CAP/CONT requirements](../../docs/design/capacity-and-continuity.md).
